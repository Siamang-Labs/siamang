# Scripts

**Builder → Scripts** adds behavior beyond asking questions. It has two
halves: a **library** of five ready-made behaviors (timers, shuffles,
matching fields, page randomization, experimental assignment), which work on
every plan, and **Custom JavaScript** *(Plus)* for anything else. This page
describes each library script exactly, how custom code runs, and where
scripts take effect.

The Scripts tab is under **More** in the Builder's tab strip.

---

## The Scripts tab

```
2 scripts. Library scripts are stored by what they do …           [+ Add script]

Script                            Kind         Trigger
Timer on q_task · 30s             library      onQuestionShow    open  edit  remove
Flag speeders                     custom JS    onSubmit          open  edit  remove
```

- The note reads: "**N scripts.** Library scripts are stored by what they do
  and regenerated by the engine; Custom JavaScript runs verbatim in the survey
  page, sandboxed from the data."
- **Add script** opens a menu of the five library scripts, each with a short
  description, and **Custom JavaScript** ("Your own code on a trigger — page,
  question, answer, submit.").
- Choosing one opens an editor card titled "New · <script>" (or "Edit ·
  <script>"). **Add** (or **Apply**) stays disabled until the required fields
  are filled. **Cancel** closes the card.
- The table lists every script with a one-line summary, its **Kind**
  (**library** or **custom JS**) and its **Trigger**. The row actions are:
  - **open**: selects the targeted question or page in Structure;
  - **edit**;
  - **remove**: deletes the script at once; use **Undo** if needed.
- With no scripts: "No scripts. Add one from the library — a timer, option
  shuffle, matching-field check — or write Custom JavaScript."
- A question that a script targets carries a **script** pill on its card in
  Structure (tooltip "A script targets this question (Scripts tab)").

Scripts are part of the questionnaire: versioned with each Save and included
in `questionnaire.py`. Library scripts are stored by what they do (for
example "timer, 30 seconds on `q_task`"), so they read clearly in the
generated Python and keep working when the engine is updated.

## The library

Library scripts pick their questions by Id. They work whether or not a
question's Id matches its variable name: Studio builds their code for the
name the answer is stored under.

### Timer on question

"Auto-advance after N seconds on one question — for timed tasks and
attention checks."

| Field | Notes |
|---|---|
| **Question** | pick from "— pick a question —" |
| **Seconds** | whole number, at least 1; default 30 |

Summary: "Timer on q_task · 30s".

- The countdown starts when the question first becomes visible. After N
  seconds the survey presses **Next** for the respondent.
- The automatic **Next** is an ordinary one. If the page has an unanswered
  **required** question (or any other message blocking the page), it is
  refused: the respondent sees the message and stays on the page. For a timed
  task, leave the timed question optional, or put it alone on its page.
- The timer runs once per question in a session.

> **Current limitation.** The timer is not cancelled when the respondent
> leaves the page early. When it fires, it presses **Next** on whatever page
> is showing at that moment, which submits the survey if that is the last
> page. Use timers only where respondents are meant to wait out the time,
> such as a stimulus shown for a fixed period, and tell them so.

### Shuffle options

"Random option order on one question (the same as the question's Randomize
switch, but seedable)."

| Field | Notes |
|---|---|
| **Question** | a question with answer options |
| **Seed** ("optional — same seed, same order") | see the limitation below |

Summary: "Shuffle options of brand_list (seed 42)". The shuffle happens when
the question is first shown (the table's **Trigger** column says `onInit`).

> **Current limitation.** The seed has no effect. Each respondent gets an
> independent random order, exactly as with **Randomize option order**. What
> stays in place is the same too: only **Other (please specify)**. To keep a
> last option last, see
> [Shuffle but keep the last option last](#shuffle-but-keep-the-last-option-last).

### Validate fields match

"Two answers must be equal (e-mail twice, code confirmation); shows a message
on the second field."

| Field | Notes |
|---|---|
| **Field A** | the first question |
| **Field B** | the second question; must be a different one |
| **Message** ("shown on field B") | the message; left empty, respondents see "Fields do not match." (the placeholder "The two entries do not match." is only an example) |

Summary: "email must match email_confirm".

- The check runs whenever the answer to **Field B** changes. If both answers
  exist and differ, the message appears under Field B and **Next** is refused
  until they match.
- The comparison is exact: `Ann@x.org` and `ann@x.org` differ.
- If the respondent corrects **Field A** instead, the message stays until
  they touch Field B again. Put Field B after Field A on the page, and say so
  in its hint.

### Randomize pages

"Content pages are served in random order for each respondent." The form
says "No settings. Terminal pages (final, screen-out, redirect) keep their
place."

- The **first** page, the **last** page and every end page (Final,
  Screen-out, Redirect) keep their positions. The other pages are shuffled
  into the remaining positions.
- Nothing is shuffled unless at least **two** pages are free to move.

Put your introduction or screener on the first page and your end pages after
the last content page. See
[Page order](Studio-Quotas-and-Randomization#page-order) for why. Summary:
"Randomize page order".

### Assign to a condition

"Draw each respondent into one experimental arm and store it in a variable —
split-ballot, vignettes, A/B stimuli. Branch on it in Logic."

| Field | Notes |
|---|---|
| **Variable** (hint "the arm is stored here — branch on it in Logic") | default `condition`. Errors: "Letters, digits and _ only, not starting with a digit." and "\"x\" is already a collected variable — pick another name." |
| **Seed** | leave empty (see below) |
| **Balance** | **Keep the arms level against their quotas** |
| **Arms** | **Code**, **Label**, **Weight**, **Share**; **Add arm**; at least two ("An assignment needs at least two arms") |

The draw happens once, before the first page. On **Add**/**Apply** the
variable is written to the codebook with the arms as its value labels. As
the hint says, you can then branch on it in Logic: a show if, hide if or
branch rule that reads the arm variable works anywhere in the survey, the
first page included. Summary: "Assign condition · 2 arms · balanced". The
full description, with balancing against quotas and branching on the arm, is
in [Experimental assignment](Studio-Quotas-and-Randomization#experimental-assignment).

> **Current limitation.** A **seeded** assignment sends every respondent to
> the same arm. Leave **Seed** empty.

## Custom JavaScript *(Plus)*

The one place in Studio where you write code: a snippet that runs in the
respondent's browser at a moment you choose.

| Field | Notes |
|---|---|
| **Name** (placeholder "Flag speeders") | optional; shown in the table |
| **Trigger** | when it runs (see below); default **onPageEnter** |
| **Target** ("optional — every one when empty") | for page and question triggers only: **— any page —** / **— any question —**, or one page or question. Questions are listed by Id; a question whose Id differs from its variable name is listed as `id → variable` (the script targets the Id, and its answer is stored under the variable). Changing the **Trigger** clears the target |
| **Code** ("JavaScript · n/2000") | up to 2,000 characters |

### Triggers

| Trigger | Hint in the form | When it runs | Target |
|---|---|---|---|
| **onInit** | "once, when the survey loads" | once, before the first page appears | none |
| **onRandomize** | "after the declared randomization ran" | right after **onInit** | none |
| **onPageEnter** | "when a page is shown (target: page name)" | each time a page is shown | page |
| **onPageExit** | "when the respondent leaves a page (target: page name)" | when leaving a page, with **Next** or **Previous** | page |
| **onQuestionShow** | "when a question becomes visible (target: question id; its answer is keyed by the variable)" | the first time a question becomes visible in the session | question |
| **onAnswer** | "when an answer changes (target: question id; its answer is keyed by the variable)" | after each change to an answer | question |
| **onSubmit** | "right before the answers are sent" | on the last page's submit, and when an end page is reached | none |

With a target, the script runs only for that page or question. Without one,
it runs for every page or question.

### What your code receives

The code runs as the body of `async function(answers, utils, api, context)`,
so `await` is allowed. The form reminds you: "Writes to answers flow back into
the store; its keys are variable names, not question ids
(answers.__errors__[variable] shows a validation message)."

| Argument | What it gives you |
|---|---|
| `answers` | the respondent's live answers, keyed by **variable name** (the name in the codebook), not by question Id. What you write into it flows back into the survey, and it is **submitted with the response** |
| `answers.__errors__` | write `answers.__errors__["<variable>"] = "message"` to show a message under a question; it also blocks **Next** until cleared. Changing that question's answer clears it |
| `answers.__options__` | `answers.__options__["<variable>"]` is the question's option list in display order; replace it to reorder the options |
| `answers.__pages__` | the list of pages in the order they will be served |
| `utils` | `shuffle(list)` (a shuffled copy), `sample(list, n)`, `clamp(value, min, max)`, `debounce(fn, ms)`, `now()` (the time in milliseconds), `formatDate(date)` (`YYYY-MM-DD`) |
| `api` | `get(url)` and `post(url, data)`: JSON requests that return the parsed reply, or `null` if the request fails |
| `context` | currently always empty |

A question that writes several variables (a matrix, a multiple-choice
question in the wide layout, MaxDiff, conjoint) keeps its answer in `answers`
under its **Id**, and its `__errors__` and `__options__` entries are keyed by
its Id too. For a matrix, MaxDiff or conjoint that answer is an object with
one entry per variable — for a matrix `trust`, `answers["trust"]["trust_police"]`
— which your data shows as one column per variable. A multiple-choice
question in the wide layout holds the list of its chosen options' variable
names (see [Multiple choice](Studio-Question-Types#multiple-choice)).

An error inside your code is written to the browser's console, and the survey
carries on.

> **Note.** The example in the comment of a new script's template uses
> `context.startedAt`, which is never set, so it never flags anyone. Use the
> examples below instead.

### Question Ids in your code

For most questions the Id and the variable name are the same, and nothing
below matters. Where they differ (a preset gives Id `q5` and variable `nps_5`,
for example), write the **variable name** in your code.

Scripts written with the Id keep working in the common forms: when Studio
builds the survey (previews and published surveys alike), it rewrites
`answers["q5"]`, `answers.q5` and the same forms on `__errors__`,
`__options__` and `__timers__` to the variable name. It does not rewrite an Id
used any other way, for example stored in a constant (`const id = "q5"`) or
used as an object key. The engine's check then warns `SCRIPT_STALE_QUESTION_ID`
("Script '<name>' still names question 'q5' as a string or a bare identifier;
its answer is stored under 'nps_5' … Where the script means the question,
write 'nps_5'."). Comments and longer strings that merely mention the Id are
not reported.

### Examples

These examples were checked against how the survey runs scripts. Replace
the variable names (`q_age`, `q_brand`) with your own, and pick the question
as **Target**.

#### Flag fast completions

Two scripts. The first stores the start time; the second compares on
submit:

```js
// Name: Start time · Trigger: onInit
if (!answers.started_ms) answers.started_ms = utils.now();
```

```js
// Name: Flag speeders · Trigger: onSubmit
if (answers.started_ms && utils.now() - answers.started_ms < 60000) {
  answers.speeder = 1;
}
```

`started_ms` and `speeder` are submitted with the response. A respondent who
resumes later keeps their original start time. Studio already records each
response's duration for you (see [[Data Quality|Studio-Data-Quality]]); this
example shows the mechanics.

#### A custom check on one question

```js
// Trigger: onAnswer · Target: q_age
const v = answers.q_age;
if (v !== undefined && v !== null && v !== "" && Number(v) < 16) {
  answers.__errors__["q_age"] = "You must be 16 or older to take part.";
}
```

#### Shuffle but keep the last option last

With the question's **Randomize option order** switched **off**:

```js
// Trigger: onQuestionShow · Target: q_brand
const key = "q_brand"; // the question's variable name, not its Id
const opts = answers.__options__[key];
if (Array.isArray(opts) && opts.length > 2) {
  const last = opts[opts.length - 1];
  answers.__options__[key] = utils.shuffle(opts.slice(0, -1)).concat([last]);
}
```

The option you put last in the Builder ("None of these") stays last. So does
a single-choice question's **None of the above**, which is always last in the
list.

### Plans

- Custom JavaScript is included from **Plus**. On Free, the **Custom
  JavaScript** menu item is disabled with a **Plus** pill (tooltip "Included
  from Plus").
- If a Save on Free carries a custom script (for example from an import),
  the tab shows "Custom JavaScript is included from Plus: this Save will not
  deploy until the custom script is removed or the plan upgraded." Publishing
  it is refused with "Custom JavaScript in the questionnaire is included from
  Plus — remove the script or upgrade to deploy this Save".
- Library scripts work on every plan.

| Where | Scripts run? |
|---|---|
| **Structure → Preview**, **Test → Walkthrough**, share preview links | yes |
| the header **Preview** build and published surveys | yes |
| **Test → Simulate** | **no**: simulation generates data from the questionnaire's structure, not from the browser |

In previews, a balanced assignment always uses the weighted draw, and `api`
requests to other sites may be blocked by those sites.

## Checks and errors

When you Save, the engine checks scripts:

- A script whose target is no longer a page name, a question Id or a
  question's variable name (a page renamed, a question deleted) makes the
  Save **errors**, so it cannot be published: "Script '<name>' targets '<x>'
  which is not a known question ID or page name." (an unnamed script shows as
  `'None'`). Renaming a page updates branch rules that point at it, but
  **not** script targets, and changing a question's Id breaks a script that
  targets the old Id unless the old Id is also the question's variable name.
  Edit the script and pick the new target.
- For **Assign to a condition**: fewer than two arms, duplicate codes, an
  empty label or a seed combined with balancing are refused. The form
  prevents all four.

The engine also returns three script **warnings**, shown in **Validation →
Engine** and with the Save (whose state becomes **warnings**). They do not
block publishing, but the script they name does not do what you meant:

| Code | Meaning |
|---|---|
| `SCRIPT_STALE_QUESTION_ID` | a custom script names a question by an Id that differs from its variable name, in a form Studio does not rewrite (see [Question Ids in your code](#question-ids-in-your-code)) |
| `SCRIPT_TARGET_IS_A_PAGE` | an **onQuestionShow** or **onAnswer** script targets a page, so it never runs. Target a question, or use **onPageEnter** / **onPageExit** |
| `SCRIPT_TARGET_IS_A_QUESTION` | an **onPageEnter** or **onPageExit** script targets a question, so it never runs. Target the page that holds the question, or use **onQuestionShow** / **onAnswer** |

The form cannot produce the last two, because changing the trigger clears the
target; they come from the **Source** tab or an import.

## Security and privacy

- Custom JavaScript runs **as part of the survey page**, with the same access
  to the page as the survey itself. It is not isolated from the page.
- Everything you write into `answers` is stored with the response and reaches
  your data like any answer.
- The code is sent to **every respondent's browser** and is readable in
  `questionnaire.py`. Never put passwords, API keys or other secrets in a
  script.
- `api.get` / `api.post` send requests from the respondent's browser. Tell
  respondents in your consent text if you contact other services.
- Custom JavaScript never runs on Studio's servers or in your analysis flows.
